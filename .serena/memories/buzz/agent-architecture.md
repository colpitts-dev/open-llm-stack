## Buzz agent architecture (source: ~/code/buzz @ ad9591c; images sha-e17cdd9)

- Agent = Nostr keypair. Durable state lives on the relay: profile (kind 0), messages, `core` memory engram (`buzz mem`), reputation. The process is a disposable body; workspace files die with it unless a volume persists them.
- Body = `buzz-acp` (harness) → stdio ACP → agent runtime (`buzz-agent`; or goose/codex/claude adapters) → stdio MCP → `buzz-dev-mcp` (tools: `shell`, `read_file`, `str_replace`, `todo`, `view_image`; `rg`/`tree` on PATH). The `buzz` CLI runs via the shell tool. Sprig image (`ghcr.io/block/buzz-sprig`) = all of these as one multicall binary, no goose.
- Harness never publishes model text. `agent_message_chunk` is only logged (`acp::stream`) and forwarded to the owner's observer pane (NIP-AO). A channel post exists only when the model runs `buzz messages send` (or `reactions add`). Silent turn = model answered in prose.
- Reply guard (in `buzz-agent`, present in both pinned images): `BUZZ_AGENT_REQUIRE_REPLY=1` → when a turn is about to end with no recognized send, the model is reminded and rerolled, max 2 reminders, shares `BUZZ_AGENT_STOP_MAX_REJECTIONS` (default 3). Recognition = a `__shell` tool call whose command text contains `messages send`/`reactions add`. Advisory, not compelling. Desktop enables it only for mesh agents by default.
- Prompt layers per message: `[Base]` compiled-in platform prompt (CLI table, publish rules, threading, memory, engineering discipline; `crates/buzz-acp/src/base_prompt.md`) → `[System]` persona prompt (`BUZZ_ACP_SYSTEM_PROMPT`, appended; `--no-base-prompt` drops base) → team instructions → `<context>` (channel uuid, reply destination, project fields) → thread context (`BUZZ_ACP_CONTEXT_MESSAGE_LIMIT`, default 12) → the event. Persona prompts must not repeat base content.
- Sessions: `BUZZ_ACP_SESSION_POLICY=channel` (default; threads share the channel session) or `thread` (each thread isolated; DMs one conversation). Sessions share memory/workspace, not context. One prompt in flight per channel; `BUZZ_ACP_AGENTS` (1–32) workers under ONE identity; `BUZZ_ACP_MULTIPLE_EVENT_HANDLING` default `steer`.
- Subscriptions: only channels the agent is a member of (`GET /api/channels?member=true`) + membership notifications auto-subscribe; DMs; `subscribe=mentions` default (needs a `p` tag → the app only resolves `@Name` for channel members). No replay of mentions from before the harness connected.
- Author gate `BUZZ_ACP_RESPOND_TO`: `owner-only` (default; needs owner via NIP-OA `BUZZ_AUTH_TAG` or `BUZZ_ACP_AGENT_OWNER`), `allowlist` (+`BUZZ_ACP_RESPOND_TO_ALLOWLIST`), `anyone`, `nobody`. Owner commands `!cancel` `!rotate` `!shutdown` (exact body + p-tag mention).
- Ownership: NIP-OA `auth` tag signed by the owner key; NIP-AA lets an owner-attested agent join a closed relay via the owner's membership; relay git grants push to agents whose owner is on the branch's push list. Desktop mints tags for its agents; no CLI found to mint one for a standalone key → server agents are standalone identities admitted via `buzz-admin add-member`.
- Heartbeat (`BUZZ_ACP_HEARTBEAT_INTERVAL`, prompt via `--heartbeat-prompt[-file]`) for proactive work; lower priority than queued events. Memory: `core` engram auto-injected; cold `buzz mem set/get`. Hooks: `_Stop`/`_PostCompact` MCP hooks behind `MCP_HOOK_SERVERS` (off by default); `buzz-dev-mcp` todo `_Stop` objects to ending with open todos.
- Info-flow: proposal only (trusted broker holding the key, audience-bound instances). Today one process serves every channel it is in with full ambient authority → separate identities per audience.
