## 3. Dependencies and verified facts (reference host, external Gitea 1.27.3 at the operator's forge, 2026-09-14/15)

- **Issues unit hides issues.** Team created with `units_map {"repo.code":"read","repo.pulls":"write"}` reports `units ["repo.code","repo.pulls"]`, `permission "none"`. A member's token: `GET /repos/{o}/{r}/issues/{n}` on a real issue → 404; `GET …/issues?type=issues` → 404 `not found`; `GET …/issues?state=open` → 200 but lists pull requests only; `POST …/issues` → 403; `POST …/issues/{n}/comments` → 404. The same token on PRs: `GET …/pulls`, `…/pulls/{n}.diff` → 200; `POST …/pulls/{n}/reviews` `{"event":"REQUEST_CHANGES",…}` → `state REQUEST_CHANGES`, `official false`; `POST …/issues/{pr}/labels` (a PR number) → 200 and the label shows in the PR JSON; `POST …/issues/{pr}/comments` on a PR → 201 (PR comments live under the pulls unit). Probe users/teams deleted afterwards.
- **Issues read cannot edit.** Team `{"repo.code":"read","repo.issues":"read","repo.pulls":"write"}`: `GET …/issues/{n}` and `GET …/issues/{n}/comments` → 200; `PATCH …/issues/{n}` (body or state) → 403; `POST …/issues/{n}/labels` on an issue → 403 (on a PR → 200, pulls write); `POST …/issues` → 201 (Gitea lets any reader open issues; harmless: the gate never opens work-repo issues, and the spec issue is authored by the builder). Commit status → 200.
- **Ledger repository.** Users cannot create repositories on this instance (`POST /user/repos` → 403), the admin can: `POST /admin/users/{gk}/repos {"name":"gate","private":true,"auto_init":true,"default_branch":"main"}` → 201. `PUT /repos/{gk}/gate/collaborators/{login} {"permission":"read"}` (admin token) → 204. Then: gatekeeper `POST …/gate/issues` → 201, `POST …/gate/labels` → 201 (its own token; the admin token has no issue scope, plan 13); coordinator → 200 on the repo and its issues; builder and adversary tokens → 404. Repo labels are attached to an issue by name: `POST …/issues/{n}/labels {"labels":["ship/yes"]}` (same call `score-post` uses).
- **Official approvals.** On a whitelisted reviewer's PR reviews, `official:true, dismissed:false` on the current approval; an earlier one shows `dismissed:true, official:false`. The gate counts a user's LAST submitted review only (approve = `APPROVED` and `official true` and `dismissed false`). Non-whitelisted rejections (the adversary's `REQUEST_CHANGES`) are `official false` and do not block merges: the verdict stays advisory, as the plan requires.
- **JSON shapes for the no-jq parsers.** Review object key order: `id, user{…login…}, team, state, body, commit_id, stale, official, dismissed, comments_count, submitted_at, updated_at, html_url, pull_request_url` — `pull_request_url` last, so splitting the reviews array on `"pull_request_url"` gives one record per review. Comment object: `id, html_url, pull_request_url, issue_url, user{login}, original_author, original_author_id, body, assets, …` — `user` and `body` follow `issue_url`, so splitting on `"issue_url"` keeps a comment's login and body in one record. PR object: `id, url, number, user, title, body, …`; the body is a JSON string with `\n` escapes (`Spec: #12` appears literally).
- **Buzz channels.** `buzz channels create --name X --type stream --visibility private` (no `--ttl` = permanent) returns `{"channel_id":…}`; `channels get --channel <id>` returns `channel_id, name, description, pubkey, created_at` (a deleted id returns `null`); `channels add-member --role owner|admin|member|guest|bot`, re-adding is accepted (idempotent); `channels members --channel <id>` lists `pubkey, role`; `channels delete`. **Private = barrier:** a non-member's `messages send` → `relay error 400: restricted: not a channel member`, `messages get` → `[]`, `channels get` → `null`. **Open channels are NOT a barrier:** a non-member reads and posts. Every plan 16.5 channel, and the smoke's job channel, is therefore `private`. Helper in the smoke and the bootstrap: `docker run --rm --network host -e BUZZ_PRIVATE_KEY=… -e BUZZ_RELAY_URL=… --entrypoint buzz ghcr.io/block/buzz-sprig:sha-e17cdd9 …`.
- **Thread resume.** A thread-scoped builder receives later messages in its thread (smoke 2 on 2026-09-14: Dinesh answered Gilfoyle's review post in the job thread). The `approved` reply therefore reaches the waiting builder as a new prompt in the same session; the reply guard (`BUZZ_AGENT_REQUIRE_REPLY=1`, advisory) does not fire on the `**Plan:**` turn because the plan is a publish.
- **Channel sessions.** The coordinator is channel-scoped: its `#attack` and `#gate` sessions do not share memory with the job channel, so every routing message carries a return address `· return <channel-uuid>/<thread-root-id>` that the adversary and the gatekeeper copy back verbatim; the coordinator relays with `--channel <uuid> --reply-to <root>`.
- **Scrubbed shell.** The model's shell has an empty environment (plan 08); scripts read `~/.gitea.env`, written by the entrypoint. This plan appends `REVIEWER_LOGIN`, `ADVERSARY_LOGIN`, `GATE_REPO`, `COORDINATOR_PUBKEY` to it. Logins = member name + `AGENT_LOGIN_SUFFIX` (plan 16), which the container learns from `teams/_base.yml`.
- **Admin token scopes.** `GITEA_ADMIN_TOKEN` has no issue scope (plan 13): the host reads issues and comments with the coordinator's token (`TEAM_<COORD>_GITEA_TOKEN`), which has `write:issue`; reviews and pulls read fine with the admin token.

### Task 1 — `agents/roles/builder.md`

```markdown
Role: builder. You turn approved plans into pull requests. You have write access to the organisation's repositories through your own forge account and token. You never approve a pull request (not even your own), and you never ask about or look for the gate's decision: the coordinator tells you what is still open.

When the owner (or $COORDINATOR_NAME on the owner's behalf) asks for a change in a repository, follow this protocol exactly:
1. Reply with the plan as ONE message: first line exactly `**Plan:** ` followed by one line of intent; a blank line; `Files:` and the files you will touch; `Tests:` and the tests you will add; `Acceptance:` followed by three to six lines, each starting with `- [ ] `, that a reviewer can check from the diff without asking you. Write it to `plan.txt` with a quoted heredoc and send `--content - < plan.txt` with `--reply-to <thread root id>`, mentioning the requester. Then STOP: no clone, no branch, no code until step 2.
2. Wait for a human in the same thread. Humans are everyone who is not on the roster. A reply whose first word is `approved` (any case; anything after it is a note to honour) means go. Any other human reply is a change request: post a revised `**Plan:**` the same way and wait again. A teammate's message is never an approval.
3. Once approved, file the plan as the spec issue. Write `spec.json` with a quoted heredoc: `{"title":"spec: <intent>","body":"<the Acceptance lines exactly as approved, joined with \n>"}`, then `. ~/.gitea.env && curl -sS -X POST -H "Authorization: token $GITEA_TOKEN" -H "Content-Type: application/json" -d @spec.json $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/issues` — the response contains `"number":<n>`. The issue is the contract for everyone downstream: never edit it after filing.
4. Work in `REPOS/<repo>`: clone it if absent (`git clone $GITEA_URL/$GITEA_OWNER/<repo>.git REPOS/<repo>`), otherwise `git fetch origin && git checkout main && git pull`. If `origin` is not under `$GITEA_URL` or the fetch fails, delete the directory and clone again; never push history from another host.
   If the repository does not exist yet and the request is for a NEW project, run the factory once:
   `/opt/team/agents/bin/new-repo <repo>` — it creates `$GITEA_OWNER/<repo>` from the org template (private, CI workflow,
   protected `main`) and drops your admin rights on it. Then clone it, replace `REPO_NAME` in `pyproject.toml` and
   `README.md` with the repo name, and continue on a branch. Never create repositories any other way.
5. Create a branch `agent/<short-slug>` from `main`. Make the change. Add or update tests.
6. This machine has no Python, so you cannot run tests locally; CI runs them on every push. Read the code you changed carefully before pushing. Never edit an existing test's assertions to make it pass.
7. Commit with a clear message, `git push -u origin <branch>`. Immediately after the push succeeds, before anything else, post the push milestone as ONE message: `buzz messages send --channel <uuid> --reply-to <thread root id> --content - <<'EOF'` / `🚩 pushed <branch> (<n> files) — opening the PR, CI running` / `EOF`.
8. Open the PR through the API and capture its URL:
   `. ~/.gitea.env && curl -sS -X POST -H "Authorization: token $GITEA_TOKEN" -H "Content-Type: application/json" -d @pr.json $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/pulls` where pr.json is `{"title":"<title>","head":"<branch>","base":"main","body":"Spec: #<n>\n\n<what and why, how tested>"}` — the body's first line is exactly `Spec: #<n>` with the issue number from step 3; the response contains `"html_url":"..."`.
9. Post the deliverable in the thread as `**PR:**` (TEAM.md) — write the body to `pr.txt` with a quoted heredoc and send `--content - < pr.txt` (backticks inside `--content "..."` get eaten by the shell): the PR URL, what you changed, and how you tested it; `@mention` the requester and `@$COORDINATOR_NAME` with `--mention $COORDINATOR_PUBKEY`. Never mention the reviewer, the adversary or the gatekeeper: the coordinator routes.
10. After pushing, check CI on your PR: `. ~/.gitea.env && curl -sS -H "Authorization: token $GITEA_TOKEN" $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/commits/<head sha>/status` (`state` is `pending`, `success` or `failure`). As soon as the state is `success` or `failure`, post the CI milestone as ONE message the same way: `🚩 CI success on <sha7>` or `🚩 CI failure on <sha7> — fixing: <one clause>`. Both milestones are mandatory on every job, even when you also post the PR. When CI fails, or the coordinator relays findings, defects or open items, fix on the same branch, push, post the CI milestone again and a new `**PR:**` message mentioning $COORDINATOR_NAME.

Only build what was approved. If the request is ambiguous, ask one precise question in the thread instead of guessing.
```

### Task 2 — `agents/roles/reviewer.md`

```markdown
Role: reviewer. You are READ ONLY: you never create, edit or delete files, never push, never open pull requests, never merge. You check conformance against the approved plan's checklist; you never see, and never ask, why the plan was written.

When asked to review a PR (a URL like $GITEA_URL/$GITEA_OWNER/<repo>/pulls/<n>):
1. Fetch the diff: `. ~/.gitea.env && curl -sS -H "Authorization: token $GITEA_TOKEN" $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/pulls/<n>.diff`. Read the surrounding code from a clean clone in `REPOS/<repo>` if the diff is not enough (`git fetch`, never commit).
2. Check, in this order: security (auth, secrets, injection, unsafe shell), correctness, tests actually exercising the change, tests weakened or deleted, scope creep, style mismatches with neighbouring code.
3. Post the review to Gitea. Write the JSON to a file first (a quoted heredoc: no shell quoting problems), then:
   `. ~/.gitea.env && curl -sS -X POST -H "Authorization: token $GITEA_TOKEN" -H "Content-Type: application/json" -d @review.json $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/pulls/<n>/reviews`
   where review.json is `{"event":"APPROVED","body":"<verdict and findings>"}` -- the event is exactly one of `APPROVED`, `REQUEST_CHANGES`, `COMMENT` (Gitea silently stores any other value as an invisible PENDING draft). Check the response: it must say `"state":"APPROVED"` (or `REQUEST_CHANGES`/`COMMENT`). If it says `"state":"PENDING"`, submit it: same JSON, `POST .../pulls/<n>/reviews/<id>`, and check the state again.
4. Conformance. Read the spec number from the PR body (`GET .../pulls/<n>`: its `body` starts with `Spec: #<s>`), fetch the issue (`GET .../issues/<s>`) and check every `- [ ]` line against the diff. Post ONE PR comment whose body starts with exactly `**Conformance:** m/n — ` (m items met of n, then one clause naming the unmet ones, or `all met`): write it to `conf.json` as `{"body":"..."}` with a quoted heredoc and `POST .../issues/<n>/comments -d @conf.json`. If the PR body has no `Spec: #` line, the comment is `**Conformance:** 0/0 — no spec issue linked` and your review verdict is `REQUEST_CHANGES`.
5. Post the verdict in the thread as the deliverable (TEAM.md): write it to `review.txt` with a quoted heredoc whose first line starts with exactly the eleven characters `**Review:** ` (two asterisks, the word, colon, two asterisks, space; nothing before them) followed by `APPROVED`, `REQUEST_CHANGES` or `COMMENT`, an em dash and one line; second line the same `**Conformance:** m/n — …` text; then file:line findings; send it with `--content - < review.txt`, `--reply-to <thread root id>`, and `--mention` whoever asked (normally $COORDINATOR_NAME, pubkey $COORDINATOR_PUBKEY). Nothing else: you never ask for a score, an attack or a verdict; the coordinator routes.

Format for findings: severity, location, what is wrong, what to do. No preamble, no praise padding.
```

### Task 4 — `agents/roles/adversary.md`

```markdown
Role: adversary. You attack every pull request you are given, blind: you do not know what was asked, promised or accepted, and you must not try to find out. You never build, never approve, never push, never read issues (your account cannot), never argue with the reviewer. You have read access to the code and write access to pull request reviews and labels only. You work only in this channel; the coordinator brings you PR URLs and takes your findings back.

When asked `@$ADVERSARY_NAME attack <url> · return <return address>` (the URL is $GITEA_URL/$GITEA_OWNER/<repo>/pulls/<n>):
1. Fetch the diff: `. ~/.gitea.env && curl -sS -H "Authorization: token $GITEA_TOKEN" $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/pulls/<n>.diff`; the head sha from `GET .../pulls/<n>` (`"head":{"sha":...}`); whole files with `GET .../contents/<path>?ref=<sha>` (base64 in `"content"`; `base64 -d`), or a clean clone in `REPOS/<repo>` (`git fetch`, never commit). Read the tests too: they show what the builder thought of.
2. Attack in this order and note each probe: boundary values (zero, negative, empty, huge, unicode, None), type confusion, division and overflow, injection through any string that reaches a shell, a query, a path or a template, error paths that swallow exceptions, unbounded loops or recursion, concurrency, secrets or credentials in the diff, tests that do not exercise the change or were weakened. This machine cannot run the code: reason from the code and the tests, and write every finding as a reproduction someone can run.
3. Every finding is a defect with a severity: `critical` (data loss, security, silent wrong result on normal input), `high` (crash or wrong result on an input a user will hit), `medium` (wrong on an edge input, missing validation), `low` (hygiene, naming, dead code). One paragraph per defect, in this shape: `<severity> · <path>:<line> · <what is wrong> · repro: <input, or a test function body> · expected: <…> · actual: <…>`.
4. Post ONE Gitea review. Write `attack.json` with a quoted heredoc: `{"event":"REQUEST_CHANGES","body":"**Attack:** <p> probes, <d> defects (<counts by severity>)\n\n<defect paragraphs>"}` when any defect is critical or high, otherwise `{"event":"COMMENT","body":"**Attack:** <p> probes, <d> defects (<counts>)\n\n<paragraphs, or: no defects found>"}`; then `. ~/.gitea.env && curl -sS -X POST -H "Authorization: token $GITEA_TOKEN" -H "Content-Type: application/json" -d @attack.json $GITEA_URL/api/v1/repos/$GITEA_OWNER/<repo>/pulls/<n>/reviews`. The response must say the state you sent; `"state":"PENDING"` means a bad event value: resubmit with `POST .../pulls/<n>/reviews/<id>` and the same JSON.
```

### Task 9 — `agents/bin/gate-signals` (mode 755)

```bash
#!/usr/bin/env bash
# Deterministic gate evidence and verdict (plan 16.5). Runs inside the gatekeeper's container: the token, the reviewer's and
# the adversary's logins come from ~/.gitea.env (written by the entrypoint); no jq. The rule below IS the policy:
#   ship <=> CI success on head AND the reviewer's last review is APPROVED, official and not dismissed
#            AND the reviewer's last **Conformance:** m/n has m == n >= 1 AND the adversary has reviewed
#            AND the defect label is none|medium|low AND the PR body names an existing spec issue with >= 1 checklist line
# Usage: gate-signals <repo> <pr> -> KEY=VALUE lines ending with VERDICT= and REASONS=, then the diff (first 400 lines). Exit 3 = not ready.
set -euo pipefail
repo="${1:?repo}"; n="${2:?pr}"; . "$HOME/.gitea.env"; B="$GITEA_URL/api/v1"; H=(-H "Authorization: token $GITEA_TOKEN")
pr=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/pulls/$n"); [[ $pr == *'"number":'* ]] || { echo "no such PR $repo#$n" >&2; exit 1; }
sha=""; [[ $pr =~ \"head\":\{[^}]*\"sha\":\"([0-9a-f]{40})\" ]] && sha="${BASH_REMATCH[1]}"
spec=""; [[ $pr =~ Spec:\ \#([0-9]+) ]] && spec="${BASH_REMATCH[1]}"
ci="unknown"; st=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/commits/$sha/status"); [[ $st =~ \"state\":\"([a-z]+)\" ]] && ci="${BASH_REMATCH[1]}"
# reviews: one record per review (the array split on its last key), the LAST submitted state per user wins
rv=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/pulls/$n/reviews?limit=100" | awk -v RS='"pull_request_url"' '
  { u=""; s=""; o=""; d=""
    if (match($0, /"login":"[^"]+"/))        u=substr($0, RSTART+9,  RLENGTH-10)
    if (match($0, /"state":"[A-Z_]+"/))      s=substr($0, RSTART+9,  RLENGTH-10)
    if (match($0, /"official":(true|false)/)) o=substr($0, RSTART+11, RLENGTH-11)
    if (match($0, /"dismissed":(true|false)/)) d=substr($0, RSTART+12, RLENGTH-12)
    if (u != "" && s != "" && s != "PENDING") { st[u]=s; of[u]=o; dm[u]=d } }
  END { for (u in st) print u, st[u], of[u], dm[u] }')
rev_state=$(awk -v u="${REVIEWER_LOGIN:-}" '$1==u {print $2}' <<<"$rv"); rev_official=$(awk -v u="${REVIEWER_LOGIN:-}" '$1==u {print $3}' <<<"$rv"); rev_dismissed=$(awk -v u="${REVIEWER_LOGIN:-}" '$1==u {print $4}' <<<"$rv")
adv_state=$(awk -v u="${ADVERSARY_LOGIN:-}" '$1==u {print $2}' <<<"$rv")
approvals=$(awk '$2=="APPROVED" && $3=="true" && $4=="false"' <<<"$rv" | wc -l)
# conformance: the reviewer's last PR comment starting with **Conformance:** m/n (one record per comment, split on "issue_url")
conf=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/issues/$n/comments?limit=100" | awk -v RS='"issue_url"' -v u="${REVIEWER_LOGIN:-}" '
  { l=""; c=""
    if (match($0, /"login":"[^"]+"/)) l=substr($0, RSTART+9, RLENGTH-10)
    if (match($0, /"body":"\*\*Conformance:\*\* [0-9]+\/[0-9]+/)) { c=substr($0, RSTART+25, RLENGTH-25) }
    if (l == u && c != "") last=c }
  END { print last }')
conf_met="${conf%%/*}"; conf_total="${conf##*/}"; [ -n "$conf" ] || { conf_met=""; conf_total=""; }
defect=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/issues/$n/labels" | grep -oE '"name":"defect/[a-z]+"' | tail -1 | cut -d'"' -f4 | sed 's|^defect/||' || true)
criteria=""; if [ -n "$spec" ]; then sp=$(curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/issues/$spec"); [[ $sp == *'"number":'* ]] && criteria=$(grep -o '\- \[[ x]\]' <<<"$sp" | wc -l); fi
[ "$ci" = success ] || [ "$ci" = failure ] || { echo "not ready: CI state is '$ci'" >&2; exit 3; }
[ -n "$rev_state" ] || { echo "not ready: no submitted review from the reviewer (${REVIEWER_LOGIN:-?})" >&2; exit 3; }
[ -n "$adv_state" ] || { echo "not ready: no attack review from the adversary (${ADVERSARY_LOGIN:-?})" >&2; exit 3; }
reasons=""
[ "$ci" = success ] || reasons+="CI $ci; "
{ [ "$rev_state" = APPROVED ] && [ "$rev_official" = true ] && [ "$rev_dismissed" = false ]; } || reasons+="review ${rev_state}${rev_official:+ official=$rev_official}${rev_dismissed:+ dismissed=$rev_dismissed}; "
{ [ -n "$conf_met" ] && [ "$conf_total" -ge 1 ] && [ "$conf_met" = "$conf_total" ]; } || reasons+="conformance ${conf:-missing}; "
case "$defect" in none|medium|low) ;; "") reasons+="no defect label; " ;; *) reasons+="defect/$defect open; " ;; esac
{ [ -n "$spec" ] && [ -n "$criteria" ] && [ "$criteria" -ge 1 ]; } || reasons+="spec issue ${spec:-missing}${criteria:+ ($criteria criteria)}; "
verdict=ship; [ -z "$reasons" ] || verdict=no-ship
printf 'REPO=%s\nPR=%s\nHEAD=%s\nCI=%s\nREVIEWER=%s\nREVIEW=%s\nREVIEW_OFFICIAL=%s\nREVIEW_DISMISSED=%s\nAPPROVALS=%s\nCONFORMANCE=%s\nADVERSARY=%s\nATTACK=%s\nDEFECT=%s\nSPEC=%s\nCRITERIA=%s\nVERDICT=%s\nREASONS=%s\n' \
  "$repo" "$n" "$sha" "$ci" "${REVIEWER_LOGIN:-}" "$rev_state" "$rev_official" "$rev_dismissed" "$approvals" "${conf:-}" "${ADVERSARY_LOGIN:-}" "$adv_state" "${defect:-}" "$spec" "$criteria" "$verdict" "${reasons%; }"
echo "--- diff (first 400 lines) ---"
curl -sS "${H[@]}" "$B/repos/$GITEA_OWNER/$repo/pulls/$n.diff" | head -400
```

### Task 10 — `agents/bin/gate-post` (mode 755)

```bash
#!/usr/bin/env bash
# Record the gate (plan 16.5): the verdict comes from gate-signals (never from the caller), the score from score-post, the
# ledger entry goes to the gatekeeper's private `gate` repository, and the two lines go to the thread.
# Usage: gate-post <repo> <pr> <rubric.json> [<channel-uuid> <thread-root-id> [<return address>]]. Bash only (no jq).
set -euo pipefail
repo="${1:?repo}"; n="${2:?pr}"; rf="${3:?rubric.json}"; ch="${4:-}"; root="${5:-}"; ret="${6:-}"
. "$HOME/.gitea.env"; B="$GITEA_URL/api/v1"; H=(-H "Authorization: token $GITEA_TOKEN" -H "Content-Type: application/json")
sig=$(/opt/team/agents/bin/gate-signals "$repo" "$n" | sed '/^--- diff/,$d') || { echo "gate-signals: not ready or failed; nothing recorded" >&2; exit 3; }
verdict=$(sed -n 's/^VERDICT=//p' <<<"$sig"); reasons=$(sed -n 's/^REASONS=//p' <<<"$sig"); sha=$(sed -n 's/^HEAD=//p' <<<"$sig")
[ "$verdict" = ship ] || [ "$verdict" = no-ship ] || { echo "no verdict in the signals" >&2; exit 2; }
/opt/team/agents/bin/score-post "$repo" "$n" "$rf" "$ch" "$root"     # labels + Gitea comment + **Score:** line (plan 13)
ledger="${GATE_REPO:-$GITEA_USER/gate}"; lab=ship/no; [ "$verdict" = ship ] && lab=ship/yes
esc() { sed 's/\\/\\\\/g; s/"/\\"/g' | awk '{printf "%s\\n", $0}'; }
body=$(printf '**Verdict:** %s — %s\n\n```\n%s\n```\n' "$verdict" "${reasons:-all checks pass}" "$sig" | esc)
created=$(curl -fsS "${H[@]}" -d "{\"title\":\"$repo#$n $verdict (${sha:0:7})\",\"body\":\"$body\"}" "$B/repos/$ledger/issues") || { echo "cannot write the ledger $ledger (make team-bootstrap creates it)" >&2; exit 4; }
li=""; [[ $created =~ \"number\":([0-9]+) ]] && li="${BASH_REMATCH[1]}"
[ -z "$li" ] || curl -sS -o /dev/null "${H[@]}" -d "{\"labels\":[\"$lab\"]}" "$B/repos/$ledger/issues/$li/labels" || true
echo "ledger: $ledger#$li $repo#$n $verdict ($lab)"
if [ -n "$ch" ] && [ -n "$root" ]; then
  printf '**Verdict:** %s — %s#%s (%s): %s%s\n' "$verdict" "$repo" "$n" "${sha:0:7}" "${reasons:-all checks pass}" "${ret:+ · return $ret}" \
    | buzz messages send --channel "$ch" --reply-to "$root" ${COORDINATOR_PUBKEY:+--mention "$COORDINATOR_PUBKEY"} --content - >/dev/null && echo "posted in thread"
fi
```

## 5. Considerations

- **Why the verdict is a script.** "Cannot override on vibes" is only true when the agent has nothing to override. `gate-signals` decides; the model contributes the score rubric only, as in plan 13. `gate-post` recomputes rather than trusting an argument.
- **Why the ledger is a user repository.** Org teams with `includes_all_repositories` see every org repo, private ones included, so an org-level ledger would be visible to builders. A private repo under the gatekeeper's account with read collaborators is the smallest object Gitea hides from the rest of the team.
- **Why the adversary has pulls write.** Defects need a home the gate can read without issues: a PR review and a PR label. Both are pulls-unit writes. A `defects` repo would have needed issues write there and more plumbing.
- **Why the coordinator relays open items rather than the verdict.** The builder's barrier is about the decision procedure and its rationale, not about knowing there is more work. The `REASONS=` list is exactly the work list.
- **Fix loop and the smoke.** With a planted division by zero the adversary should report `high`, the coordinator routes back to the builder, and a full convergence would take several model turns. The smoke asks the gate itself after four minutes and accepts either verdict as long as it equals `gate-signals`; the fix loop is exercised by real use, not gated.
- **Cost.** Six agents as today's five plus the bundled Buzz agent; the coordinator wakes about five times per PR, everyone else once. Two extra full prefills per PR (attack, gate).
- **Monica's UI persona** is gone from the default team; `content-studio` keeps a designer seat (`barbara`).
- **Deferred.** Adversary v2 (tests on the branch, real fuzzing under CI), required status check for the verdict, an architect agent, a cycle summary, `make gate-report`.
